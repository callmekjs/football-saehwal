### 오전 — 무엇을 만들 것인가

기획서 PDF 14쪽을 읽고 스코프를 잡았다. 결론은 **기획서 전체를 만들 시간이 없다**는 것이었다.

| | |
|---|---|
| 가용 시간 | 하루 약 5시간 × 6일 = 30시간, 배포·문서 빼면 순수 개발 27시간 |
| 기획서 1차 범위 | 축 4종 · 국면 3종 · 화면 3종 · 검증 봇 5종 = **31~39시간** |
| 판정 | 초과. 무엇을 버릴지 정하지 않으면 미완성으로 제출하게 된다 |

**접근 A(수직 완성)를 택했다.** 국면 하나를 끝까지 완성한 뒤 늘린다. 기획서가 "국면 = JSON 한 덩어리, 엔진은 순수 함수"로 설계돼 있어 **엔진이 완성되면 국면 추가 비용이 거의 0**이기 때문이다. 구조적으로 수직 완성이 유리한 설계였다.

대회 규칙에서 세 가지가 계획을 바꿨다.

- **마감이 8/3 10:00이고 그 이후 커밋은 실격.** 일요일 밤이 진짜 마감이다.
- **"동적 인터랙션이 실제로 작동하지 않으면 해당 기능은 평가에서 제외."** 반쯤 만든 기능은 0점이다. 스코프를 줄이는 쪽이 점수상 유리하다.
- **1차 관문이 대중 투표**(제출팀 60% + 참가팀 20%). 투표자 대부분이 같이 참가한 개발자다. 수십 개를 빠르게 훑는다. **75초짜리라 끝까지 플레이된다는 것 자체가 경쟁력**이고, 대신 첫 15초 온보딩의 우선순위가 올라간다.

### 폐기한 것 — "실제 감독의 선택 vs 나의 수"

기획서의 핵심 셀링 포인트였으나 **만들 수 없다고 판단했다.**

공개 데이터로 알 수 있는 것은 교체 기록뿐이다. "78분에 라인을 내렸다" 같은 인게임 전술 변경은 **어디에도 기록이 없다.** 지어내면 실존 인물이 하지 않은 결정을 했다고 쓰는 것이고, 대회 규칙의 명예훼손 조항에 걸린다.

더 근본적으로 **기획서 5.1절이 이미 "국면은 창작된 배치다"라고 적고 있었다.** 창작한 국면에 실제 감독이 있을 리 없다. 바둑 사활문제집에 프로기사 이름이 없는 것과 같다.

→ 비교 대상을 **설계된 정답 경로**로 교체. 병렬 재생 기능 자체는 그대로 유지된다.

### 실존 선수 이름 배제

이 게임의 실점 공식은 **"우리 수비수 중 가장 느린 선수"를 실점 원인으로 기계적으로 지목**한다. 실명이 붙으면 "이 선수 때문에 졌다"가 자동으로 생산된다. 문구를 조심해서 막을 수 있는 게 아니라 **구조가 그렇게 생겼다.**

그리고 **이름은 계산 어디에도 쓰이지 않는다.** 빼도 아무것도 깨지지 않는다.

→ 선수는 등번호와 포지션으로만 식별. 팀 이름도 "우리 팀 / 상대". 사진·엠블럼·유니폼 파일 0개.

### 데이터 조사 — 능력치는 8분의 1이었다

여섯 각도(엔진 계산 / 화면 표시 / 문제 정의 / 검증 / 저작권 / 조달 현실성)로 필요한 데이터를 훑었다. 137개 항목이 나왔고 **전부 만들면 77시간**이었다. 예산은 12시간이다.

가장 중요한 발견은 **기획서에 승수만 있고 곱할 원본이 없다**는 것이었다.

- "전진 성공 ×1.30" — 곱해질 기본 확률이 없다. 없으면 공이 한 칸에 영원히 머문다
- "볼 탈취 ×1.40" — 없으면 압박은 체력만 깎고 이득이 0이라 정답 경로가 압박을 절대 안 쓴다
- **"골이 들어간 다음 무엇을 하는가"가 통째로 없다** — 첫 실점 순간 경기가 이어지지 않는다

### 국면 5종 확정

원래 기획서는 8국면이었으나, 실시간 사활문제라는 개념에 맞춰 5개를 새로 설계했다.

| # | 상황 | 목표 | 직관 → 정답 |
|---|---|---|---|
| 1 | 0-1 지고 있음 · 70분 | 동점 이상 | 몰아넣는다 → 좌우로 벌려야 길이 난다 |
| 2 | 1-0 이기고 있음 · 70분 | 지키기 | 버틴다 → 잠금을 푼다 |
| 3 | 1-1 · 80분 | 무승부 또는 승리 | 밀어붙인다 → 되돌려 안정시킨다 |
| 4 | 1-0 이기는데 우리 퇴장 · 80분 | 지키기 | 다 잠근다 → 잠그면 더 맞는다 |
| 5 | 0-1 지는데 상대 퇴장 · 80분 | 동점 이상 | 다 밀어붙인다 → 옆으로 돌아야 한다 |

**설계의 핵심은 `initialTactics`(앞 감독이 잘못 걸어놓은 지시)다.** 중립에서 시작하면 아무것도 안 해도 통과해버려 퍼즐이 성립하지 않는다. 판마다 잘못 걸린 것이 달라서 과제도 전부 달라진다.

### 사전 검증에서 확인한 두 가지

국면 5개를 각각 설계하고 두 명씩 반박시켰다. 두 가지가 나왔다.

**1. "순서가 결과를 가른다"는 이 모델에서 성립할 수 없다.**

기획서의 레버는 **확률에 곱하는 승수**다. 곱셈에는 순서가 없다. `2×3×5`나 `5×2×3`이나 30이다. 레버를 어떤 순서로 당기든 결과가 같은 것은 계산 문제가 아니라 **설계상 필연**이었다.

→ 순서를 **교체 카드**로 옮겼다. 카드는 3장뿐이고 회수가 안 된다. 되돌릴 수 없는 자원이라 쓰는 순서가 실재한다. 그리고 "느린 수비수를 먼저 빼고 라인을 올린다 / 반대로 하면 그 사이에 뚫린다"라는 선행 조건이 성립한다.

**2. 지키는 국면은 무개입으로도 통과한다.** 이 예측은 오후에 실측으로 확인됐다.

뭉쳐놓으니 1골 차 리드가 완충재로 작용해 **무개입 통과율이 77.1%**가 나왔다. 아무것도 안 해도 열 판에 여덟 판을 통과한다. 퍼즐이 아니었다.

**② 배후 침투 판정에서 같은 난수를 두 번 썼다**

계획서에 쓴 코드가 `d.behindShot`을 조건 하나에서 두 번 소비하고 있었고, 앞쪽 조건은 약분하면 항상 참이었다. 계획을 실행하며 발견해 고쳤다.

**③ 승수의 정확한 값을 검사하던 테스트**

`expect(c.setPiece).toBeCloseTo(2.8)` 같은 테스트는 밸런싱으로 값을 조정할 때마다 깨진다. 방향과 비율 검사(`low.setPiece > mid.setPiece * 2`)로 바꿨다.

### 밸런싱 실측

```
시드 400개 × 국면 2개 × 27조합

국면            무개입   최선(조합)      격차     스프레드  판정

```

합격 기준은 무개입 50% 이하, 격차 20%p 이상이다. **둘 다 통과.**

조정한 상수 3개 — 상대 기본 위협을 낮추고(`O0` 0.011→0.0095, `B0` 0.002→0.0016) 라인 낮음의 세트피스 승수를 올렸다(2.8→3.4).

**설계 가설이 실측으로 확인됐다.** 27조합 중 성적 하위 3개가 두 국면 모두 **전부 "라인 낮음"**이다. **깊이 잠글수록 오히려 더 맞는다** — 내려앉으면 걷어내게 되고, 걷어내면 세트피스를 준다. 이것이 안 나왔으면 국면 2와 4를 다시 설계해야 했다.

### 엔진을 명단에 연결

지금까지 `minDefenderSpeed`는 국면 데이터에 박힌 숫자였다. 이제 **피치 위 수비수에서 계산**한다. 교체가 들어가는 순간 배후 실점 확률이 즉시 바뀐다.

상태 구조도 바꿨다. `stamina: Record<string, number>` → `players: PlayerState[]`. 각 선수가 피치 위인지, 체력이 얼마인지, 경고를 받았는지, 이탈했는지를 개별로 추적한다. 내일 교체·퇴장·부상이 붙으려면 필요한 구조이고, **엔진이 100줄일 때 바꾸는 것이 훨씬 싸다.**

명단에 없는 선수를 국면이 지목하면 즉시 실패하게 했다. 토요일에 국면 다섯 개를 손으로 채울 때 오타를 여기서 잡는다.

- **국면 4의 무개입 49.3%가 상한에 근접.** 내일 퇴장·부상이 붙으면 움직인다.
- **두 국면의 최선 조합이 여전히 동일(1/2/2).** 국면끼리 정답이 갈리려면 압박 축을 억제하는 퇴장 위험이 필요하다. 내일 붙인다.

### 밤 — 경기 중 사건과 교체 카드

**압박 축이 드디어 대가를 갖게 됐다.** 여기까지 압박은 체력만 깎고 이득만 주는 축이라 사실상 고를 이유가 없었다. 경고 보유 선수가 피치에 있을 때 강 압박을 유지하면 퇴장 위험이 붙도록 했다(틱당 0.00035, 750틱 누적 약 23%). 이것이 압박이 값을 갖는 유일한 통로다.

파울 → 경고 → 두 번째 경고 시 퇴장의 사슬도 넣었다. 부상은 체력 25 아래에서만 발동하고 **교체 카드를 한 장 강제로 소모한다** — "쓸 수 있었던 카드를 못 쓰게 되는" 경험이 감독직의 본질에 가깝다.

**교체는 6초 뒤에 반영된다.** 즉시 반영하면 "늦게 쓰면 늦게 듣는다"가 성립하지 않는다. 이 지연이 있어야 순서가 실재한다.

우리가 열 명일 때의 커버 공백 계수(×1.22)를 이제야 실제로 배선했다. 그전까지 국면 4는 열 명으로 시작했는데 계산상 아무 불이익이 없었다.

### 빠져 있던 장치를 찾았다 — 폭의 수비 쪽 대가

세 국면을 측정했더니 **최선 조합이 전부 `1/2/2`로 같았다.** 만능 조합이 존재한다는 뜻이고, 그러면 "판마다 다른 판단이 필요하다"는 이 기획의 핵심 주장이 무너진다.

원인은 튜닝이 아니라 누락이었다. 설계서에는 "좁게 → 중앙 차단 / 넓게 → 중앙 노출"이라고 적어놓고 **구현에서는 폭이 우리 공격에만 영향을 주고 실점에는 아무 영향이 없었다.** 넓게가 공짜였다.

대가를 붙이자 정답이 갈렸다. 지키는 판은 좁게, 쫓는 판은 넓게.

### 측정 방법을 고쳤다

처음에 시드 400개로 재고 "정답이 갈렸다"고 판단했는데, **성급했다.** 400개면 60% 근처에서 표준오차가 2.4%p라 조합끼리 1~2%p 차이는 노이즈와 구분되지 않는다.

시드를 1200개로 올리고, 1위와 통계적으로 구분되지 않는 조합의 개수를 함께 출력하게 했다. 이제 "1위가 무엇인가"가 아니라 "1위가 의미 있게 1위인가"를 볼 수 있다.

### 최종 측정

```
■ 길이 막혔다   무개입 15.0% → 최선 38.6% (2/1/2)   격차 23.6%p
■ 잠긴 문      무개입 47.0% → 최선 71.0% (1/1/2)   격차 24.0%p
■ 한 명이 없다  무개입 38.2% → 최선 64.3% (1/2/2)   격차 26.1%p
```

세 국면 전부 합격. 최하위 조합이 국면마다 다르다 — 쫓는 판은 `0/2/0`, 지키는 판은 `0/0/0`·`0/0/2`.

테스트 84개, 타입 오류 0.

### 밸런싱 3회전에서 멈춘 이유

상수를 세 번 조정했다. 매번 한 국면이 좋아지면 다른 국면이 나빠져서, 국면 전체에 걸리는 손잡이(`A0`)가 아니라 **한쪽에만 걸리는 손잡이**를 찾아야 했다. 상대 밀집도에 연동된 폭 계수가 그것이었다 — 상대가 내려앉은 판(쫓는 국면)에서만 크게 작용한다.

세 국면이 다 합격한 시점에서 멈춘다. 토요일이 밸런싱 날이고 그때는 국면이 다섯 개다. 지금 더 맞춰봐야 그때 다시 맞춰야 한다.

### 알고 넘어가는 것

- **지키는 두 국면은 상위권이 평평하다.** 1위와 구분되지 않는 조합이 11개, 15개. "이 조합만이 정답"이 아니라 "라인을 내리면 안 된다" 수준의 구분이다. 국면을 다섯 개로 늘리면서 이 부분을 조여야 한다.
- **총 득점 1.5~1.8골 / 15분.** 목표 구간 0.9~1.4를 넘는다.
- **쫓는 판 최선 38.6%.** 심사자가 한 번에 성공하기 어렵다. 국면 순서를 쉬운 판부터 배치해 완화한다.

## 2026-07-28 (화) — 관전 연출 3차: 공 물리 · 슛 판단 · 골키퍼

사용자가 화면을 보고 세 가지를 지적했다. 셋 다 여섯 판씩 돌려 숫자를 뽑고
나서 고쳤다. 진단 스크립트는 커밋 전에 지웠다.

### ① 공에 물리가 없었다

`moveBall()` 이 공을 목표 지점까지 등속으로 보내고 **도착하면 속도를 0으로**
만들었다. 차인 공이 허공에서 서는 것은 축구가 아니다.

이제 공은 `x·y·z` 와 `vx·vy·vz` 를 가진다.

- **구름 감속** — 축구공의 구름 저항 계수는 짧게 깎은 천연 잔디에서 대략
  0.055다. `a = μ·g = 0.54 m/s²`. 이 값이면 초속 20미터 땅볼 패스가 20미터를
  가도 19.4m/s 로 거의 안 죽는다. 다만 이것만으로는 세게 찬 공이 300미터를
  굴러야 서기 때문에, 속도에 비례하는 잔디 저항(`0.1·v`)을 더했다.
- **튕김** — 반발계수 0.6 (잔디 위 기준. 딱딱한 바닥은 0.83).
- **가로 속도 손실은 충돌 세기에 비례한다.** 처음에 고정 0.78 로 뒀더니
  살짝 뜬 슛이 세 번 튀는 동안 22%씩 잃어 초속 30미터가 8미터가 됐다.
  골이 화면에 뜨는 데 4.7초가 걸렸다. `1 - 충돌속도×0.035` 로 바꿨다.

패스가 목표 지점에서 서지 않으므로 **받는 방식도 바뀌었다.** 도착 판정이
아니라 **지나가는 공을 잡는 것**이다. 잡는 반경은 공이 빠를수록 좁다
(초속 24미터 이상 1.05m, 정지 2.3m). 인터셉트가 저절로 나온다 — 패스 길목에
서 있으면 잡힌다.

**걱정했던 "공이 발에 있는 시간" 은 안 줄었다.** 43.0% → 43.0%. 주인 없는
공은 오히려 13.0% → 2.0% 로 줄었다. 굴러가는 공을 앞질러 쫓아가게 했기
때문이다.

### ② 패스만 하고 슛을 안 쐈다

측정: **박스 안(골라인 16.5m)에서 패스 26회 대 슛 7회.** 슛 거리 중앙값이
47미터, 최대 89미터였다 — 자기 진영에서 상대 골대로 때리는 장면이 절반이
넘었다는 뜻이다.

원인은 두 가지였다.

1. `decide()` 에 **슛이라는 선택지 자체가 없었다.** 슛은 시뮬이 알려줄 때만
   나왔다. 실제 축구의 판단(박스 안 각이 열리면 대부분 슛, 25m 밖은 대부분
   패스)을 넣었다. 우리 팀이든 상대든 공을 가진 쪽이 같은 함수를 거친다.
2. 시뮬이 "슛"이라고 알리면 **어디에 있든 그 자리에서 쐈다.** 사정거리
   32미터 검사를 넣고, 밖이면 기다리게 했다.

결과: 박스 안 패스 1회 대 슛 14회. 슛 거리 중앙값 15.5m, 최대 32m,
자기 진영 슛 0회. 판당 슛 4.0회 — 90분 환산 24회로 실제 축구와 같다.

**시뮬 결과는 안 건드렸다.** 화면에서 새로 생긴 슛은 전부 `willScore=false`
라 골키퍼에게 막히거나 골대를 벗어난다. 점수판을 올리는 것은 시뮬이 골이라고
알려줄 때뿐이다. `npm run sim` 숫자가 한 자리도 안 바뀐 것으로 확인했다.

### ③ 골키퍼 계산식이 뒤집혀 있었다

`out = clamp(14 - 공까지거리 × 0.25, 1.5, 9)` — **공이 가까울수록 앞으로
나온다.** 상대가 우리 박스 안까지 들어온 순간 골키퍼가 골문에서 가장 멀리
나가 있었다는 뜻이다. 실측 중앙값 10.9미터, 최대 14.8미터.

실제 골키퍼는 반대다. 공이 멀면 페널티 지역 앞까지 나와 있고(스위퍼 키퍼),
가까워지면 물러나 골문을 덮는다. `out = clamp(공까지거리 × 0.2, 1.3, 10)`.

옆으로 서는 자리도 고쳤다. 전에는 공 y 를 0.45배로 따라가 골대 폭의 세 배까지
벌어졌다. 이제 **골문 중앙과 공을 잇는 선 위**의 점을 기하로 계산한다.

- 상대 공격 중(공이 30m 안) 골라인에서 10.9m → **5.9m**
- 골라인 10미터 넘게 나온 비율 14.7% → **0%**
- 페널티 지역(16.5m)을 넘는 일이 없다

골키퍼가 공을 잡으면 그 자리에서 앞으로 길게 찬다. 경기 규칙 12조대로
**공을 잡은 골키퍼는 아무도 못 뺏는다.**

### 작업 중 찾은 결함 세 개

셋 다 "점수판은 올라갔는데 화면에 골이 없다" 를 만들고 있었다.

1. **반칙 휘슬이 득점 슛을 가로챘다.** 골대로 날아가던 공이 반칙 지점으로
   순간이동했다. 슛이 날아가는 중에는 휘슬을 불지 않는다 — 어드밴티지다.
2. **0.7초 간격으로 들어간 두 골이 서로를 덮어썼다.** 예약 자리가 하나뿐이라
   뒤엣것이 앞엣것을 지웠다. 줄(큐)로 바꿨다.
3. **골 예약의 시계가 데드볼 중에 멈춰 있었다.** 스로인을 기다리는 동안
   골 장면이 그만큼 밀렸다.

### 억지 슛 대신 골망 컷을 택했다

시뮬이 골이라고 알린 순간 그 팀 선수가 아무도 골대 근처에 없을 때가 있다.
전에는 공을 아무에게나 옮겨 쐈고, 그래서 **81미터짜리 골**이 나왔다. 공이
골대까지 3.5초를 굴러가 골 장면이 득점보다 6초 늦었다.

38미터를 넘으면 슛을 만들지 않고 **중계처럼 골망이 흔들리는 장면으로 컷한다.**
안 나오는 골보다 낫고, 있을 수 없는 슛보다도 낫다. 실측으로 골 셋 중 하나가
슛으로 들어가고 둘은 컷이다.

근본 해결은 화면 쪽 공격이 상대 박스까지 도달하는 빈도를 올리는 것인데
(현재 상대 골대 25m 안 점유가 경기의 4.4%), 대형 로직을 크게 손봐야 해서
남겨뒀다.

### 테스트 148개 → 160개

고친 것을 방향과 비율로 박았다. 조정 대상 숫자는 안 박았다.

- 살아 있는 공은 0.1초에 속도가 절반 아래로 안 떨어진다 (물리)
- 굴러가는 공은 저절로 빨라지지 않는다 (마찰)
- 뜬 공이 있고, 떨어져서 튄다 (체공·튕김)
- 박스 안에서는 슛이 패스보다 많다 / 25m 밖에서는 패스가 슛보다 많다
- 가까울수록 슛 비율이 높다 (구간별 단조)
- 우리 팀과 상대가 같은 기준으로 쏜다
- 공이 가까울수록 골키퍼가 골라인에 붙는다
- 골키퍼는 페널티 지역을 넘어 나가지 않는다

기존 테스트 네 개는 **재는 방법**을 고쳤다.

- 골 장면 관련 두 개 — 한 판이 아니라 여섯 판을 합산한다. 한 판에 골은
  한두 번뿐이고 그중 일부는 골망 컷이라, 한 판만 보면 표본이 0이 된다.
- 대형 관련 두 개 — **골키퍼가 공을 잡은 순간을 뺀다.** 골키퍼 소유는 그 팀
  소유 중 가장 깊은 자리이고 상대 골키퍼가 들면 가장 높은 자리라, 두
  상황이 양쪽 평균을 반대로 끌어당겨 실제 차이를 지운다. 골키퍼 소유가
  전체의 10%였고, 그것만 빼자 공 위치 차이가 1.5m 에서 11.4m 로 커졌다.
- 재개 테스트 — 앞뒤(x) 이동이 아니라 **이동 거리**로 잰다. 킥오프는 뒤로
  빼거나 옆으로 여는 것이 정석이라 x 는 그대로인 채 좌우로만 갈 수 있다.

### 밸런스 불변 확인

```
■ 길이 막혔다   무개입 11.0% → 최선 32.5%   격차 21.5%p   합격
■ 잠긴 문      무개입 47.0% → 최선 71.0%   격차 24.0%p   합격
■ 한 명이 없다  무개입 38.2% → 최선 64.3%   격차 26.1%p   합격
```

작업 전과 **한 자리도 다르지 않다.** 관전 연출이 한 방향으로만 흐른다는 것이
실측으로 확인됐다.

## 2026-07-28 (화) 저녁 — 화면의 표시를 읽을 수 있게

사용자가 물었다. **"중간에 6번 밑에 빨간색 저건 뭐야? 노랑색도 있고"**

만든 사람이 자기 화면의 표시를 못 읽었다는 뜻이다. 심사자는 더 못 읽는다.

### 색이 두 가지 뜻을 지고 있었다

- **빨강** = 상대 팀(`#e0564b`) **이면서** 체력 고갈(같은 `#e0564b`).
  상대 선수의 체력 표시는 빨간 원 위에 빨간 호를 그리는 것이라
  **원리적으로 보일 수가 없었다.**
- **노랑** = 경고(`#e8c33c`) **이면서** 수비라인 안내선(같은 `#e8c33c`).
  서로 아무 관계 없는 것을 같은 색으로 말하고 있었다.

색을 나누는 것만으로는 부족하다. 색은 네다섯 개를 넘으면 사람이 못 외운다.
**모양이 뜻을 지게** 바꿨다.

| 무엇 | 전 | 후 |
|---|---|---|
| 경고 | 노란 링 | 노란 **카드**(네모) |
| 퇴장 | 없음 | 빨간 **카드** |
| 부상 | 없음 | **흰 바탕에 빨간 십자** |
| 체력 바닥 | 빨간 호 | **지친 얼굴** |
| 수비라인 | 노란 점선 | 하늘색 점선 |

### 이모티콘을 안 쓴 이유

폰 화면(폭 375px)에서 캔버스 폭이 343px, 선수 반지름이 7.2픽셀이다.
배지를 선수 반지름에 비례시키면 5픽셀이 되어 아무 뜻도 전달하지 못한다.
이모티콘은 13픽셀 밑으로 내려가면 뭉개지고, 폰 기종마다 그림도 다르다.

그래서 **최소 픽셀 크기를 보장하고**(`max(7.2, r×0.75)`), 얼굴은 Canvas
기본 도형으로 직접 그렸다 — 아래로 처진 눈, 아래로 굽은 입, 땀 한 방울.
십자가는 원래 이모티콘에 그 그림이 없다(🏥 병원, ⛑️ 헬멧, 🩹 반창고).

### 배지는 선수 원 바깥에 붙인다

처음에 원 위에 얹었더니 **등번호를 통째로 가렸다.** 등번호는 누구를
교체할지 정하는 유일한 단서다. 실제 화면에서 확인하고 바깥으로 옮겼다 —
경고는 오른쪽 위, 체력은 왼쪽 위.

### 부상·퇴장 선수가 소리 없이 사라지고 있었다

`engine.ts` 는 부상이 나는 **그 틱에 즉시** `onPitch: false` 로 만든다.
화면에서는 사람이 그냥 없어지고, 관전자는 우리가 열 명이 된 것조차 모른다.

시뮬을 늦출 수는 없다. 교체 카드 강제 소모와 커버 공백 계수가 그 시점에
물려 있고 밸런스가 걸려 있다. 대신 **화면에만 잔상을 남겼다.** 로그의
`INJURY`·`SEND_OFF` 를 읽어 쓰러진 자리를 기억하고, 부상은 3.4초 퇴장은
2.6초 동안 누운 채로 그린 뒤 서서히 사라지게 한다. 시뮬 결과에서 파생만
하므로 한 방향 규칙에 어긋나지 않는다.

로그 커서를 **반칙용과 이탈용으로 따로 뒀다.** 이탈은 대형을 다시 짜기
전에 읽어야 쓰러진 자리를 알 수 있고, 반칙은 세리머니 중에는 흘려보내야
한다. 하나로 합치면 둘 중 하나가 반드시 틀린 자리에서 읽힌다.

### 등번호 0번 유령

작업 중 찾았다. 열 명용 배치는 자리가 열 개인데, 부상이나 추가 퇴장으로
**아홉 명이 되면 남는 자리에 등번호 0번인 선수가 그려졌다.** 화면에서
직접 봤다 — "우리 10명"이라고 적혀 있는데 피치에는 0번이 뛰고 있었다.
자리 수를 실제 인원으로 자르는 것으로 고쳤다.

### 희소한 사건을 어떻게 확인했나

부상은 체력 25 미만인 선수가 있을 때만, 그것도 틱당 0.0004 확률로 난다.
한 판 봐서는 안 나온다. 체력이 가장 낮은 국면(제3국면)에 강 압박을 걸고
**200판을 돌려 부상 47회·퇴장 56회**를 확인했다. 사건당 잔상 프레임이
29.2개로 의도한 26~34 구간 안이다.

테스트에는 열두 판을 합산해 넣었다. 안 나오는 것을 "고쳤다"고 할 수 없으므로
**부상과 퇴장이 실제로 일어나는지부터 검사한다.**

## 2026-07-28 (화) 저녁 — 교체·스로인·연출 시계·갑자기 터지던 골

사용자 지적 네 가지. 재보니 **뒤의 셋이 같은 뿌리**였다.

### 교체가 화면에 반영되지 않았다 (1차 원인)

재구성 조건이 "포메이션이 바뀌었나 / 인원이 줄었나"뿐이었다. 열한 명이
열한 명으로 유지되는 교체는 둘 다 해당하지 않아 화면이 갱신되지 않았다.
실측으로 **경기의 76%(4500프레임 중 3420) 동안 화면 명단이 시뮬과 어긋나
있었다.**

자리 나누기도 배열 순서였다. 명단에서 빠진 선수는 배열에서 사라지고 새로
들어온 선수는 맨 뒤에 붙으므로, 교체 한 번에 뒤쪽 선수 전원이 한 칸씩
밀렸다. 자리 번호를 선수에게 붙여 **뛰던 선수는 자리를 지키게** 했다.
어긋난 프레임 3420 → 0.

교체 장면도 붙였다. 화면이 1.2초 멈추고 나가는 선수는 터치라인으로 걸어
나가며(빨간 화살표), 들어오는 선수가 그 자리로 들어온다(초록 화살표).
1.2초의 근거: 압축비가 12:1이라 실제 교체 20~30초는 2초 남짓인데, 카드가
세 장이라 2초씩이면 75초의 8%가 죽는다. 1.2초면 4.6%다.

### 그런데 사용자가 또 "교체가 안 된다"고 했다 (진짜 원인)

숫자로는 고쳐졌는데 눈으로는 아니었다. **브라우저에서 등번호를 직접
세면서** 찾았다.

`Pitch.tsx` 가 연출을 **프레임 간 실제 경과 시간**으로 진행하고 있었고,
한 프레임에 최대 0.05초로 잘라놨다. 프레임이 밀리면 잘라낸 만큼은 영영
사라진다. 시뮬은 절대 시각으로 750틱을 정확히 도는데 연출만 느려지므로
둘이 점점 벌어진다. 실측으로 **시뮬이 90분을 지나는 동안 화면은 2초밖에
진행하지 못했다.**

교체도, 골 장면도, 스로인도 안 나오는 것이 전부 이 하나였다. 사용자가 본
것은 "교체가 안 된다"였지만 실제로는 **화면 전체가 슬로모션이었다.**

이제 목표 시각이 언제나 `tick × 0.1초`이고, 뒤처졌으면 한 프레임 안에서
여러 번 나눠 진행해 따라잡는다. 초당 60프레임이면 실시간의 스물네 배까지,
초당 다섯 프레임으로 떨어져도 두 배는 따라잡는다.

같이 잡은 것: "다시 풀기"로 다시 시작하면 시뮬은 0틱으로 돌아가는데 연출은
지난 경기의 배치와 점수를 그대로 들고 있었다.

### 스로인이 발로 차는 패스였다

자리 잡는 코드는 있었다. 문제는 그 뒤였다 — 공을 받은 선수가 평범한 패스를
했고, 패스는 초속 26미터까지 나가며 24미터를 넘으면 롱볼로 뜬다. 손으로
던진 공이 40미터를 날아가고 있었다.

두 손으로 머리 위에서 던지므로 릴리스 높이가 2.1미터다. 실측 던진 거리
중앙값 11.3미터(5.8~15.4), 속도 중앙값 초속 8.9미터(7.8~12.0)로 실제
축구의 스로인 구간(10~20미터, 초속 8~14미터)에 들어간다.

### 갑자기 터지던 골 — 뿌리는 소유권이었다

골이 난 순간마다 무엇이 있었는지 세 국면 × 시드 24개로 쟀다.
**골 84회 중 54회(64%)가 슛이 아예 없었다.** 공이 중원에 있다가 곧바로
골망이 흔들린다.

원인은 더 앞에 있었다. **화면의 공 주인이 시뮬과 경기의 40% 동안 달랐다**
(일치율 60.3%). 화면은 시뮬의 소유 팀이 **바뀌는 순간에만** 맞추는데, 그때
공이 날아가는 중이거나 죽어 있으면 그 전환을 그냥 버렸다. 공은 경기의 40%를
공중에서 보내므로 전환의 상당수가 조용히 사라졌다.

그래서 시뮬이 "이 팀이 골"이라고 알린 순간 화면에서는 그 팀이 반대편
골문 앞에서 수비를 하고 있었다.

셋을 고쳤다.

1. 어긋난 채 흐른 시간을 재서 0.5초가 넘으면 시뮬 쪽으로 되돌린다.
   **매 프레임 강제로 맞추면 안 된다** — 화면에서 방금 태클로 뺏은 공이
   곧바로 되돌아가 압박이 무의미해진다.
2. 골 예약이 걸린 팀이 공을 안 가지고 있으면 유예 없이 즉시 넘겨준다.
3. 그 팀의 앞선을 밀어올려 길게 보낼 자리를 만들고, 기다리는 시간을
   3.0초에서 4.2초로 늘렸다.

| 무엇 | 전 | 후 |
|---|---|---|
| 소유 팀 일치율 | 60.3% | 76.9% |
| 슛 없이 처리된 골 | 64% | 20% |
| 슛 직전 전개 시간 중앙값 | 1.6초 | 2.5초 |
| 소유 전환 | — | 판당 34회 (실제 축구 15분 35~50회) |

소유 전환이 실제 축구 범위 안이라 공이 왔다 갔다 하지도 않는다.

### 검증 방법을 고쳤다

골·골킥·박스 안 슛은 한 판에 한두 번뿐이다. 여섯 판으로 비율을 재면 한
번의 차이로 판정이 뒤집혀 **밸런싱과 무관한 변경에도 테스트가 깨진다.**
그런 드문 사건만 쓰는 스물네 판짜리 표본(`WIDE`)을 따로 뒀다.

기준값도 근거를 붙였다. "골은 대부분 슛으로 들어간다"는 시드 60개로 재면
68%(우리 득점 73% · 실점 63%)이고, 스물네 판에 잡히는 골 서른 개의
표본오차가 ±8%p 라 기준을 0.5로 뒀다 — 고치기 전(36%)은 확실히 걸리고
정상 범위에서는 안 흔들린다.

골키퍼가 박스 안에서 얼마나 나가 있는지도 최댓값이 아니라 중앙값으로 잰다.
공이 갑자기 박스로 들어오면 골키퍼는 물러나는 중이고, 그 몇 프레임의
최댓값은 자리 잡는 실력이 아니라 달리는 속도의 문제다.

검증 코드의 결함도 하나 잡았다. 슛 거리를 직전 프레임의 볼 소유자 자리로
재고 있었는데, 한 틱 안에 소유가 바뀌면 엉뚱한 사람의 자리로 재게 된다 —
105미터짜리 슛이 잡혔다.

## 2026-07-28 (화) 밤 — 한 경기의 운과 감독의 판단을 분리하다

사용자가 말한 핵심은 플레이가 끝난 뒤 **더 나은 전술을 알려주는 것**이다.
기존 종료 화면은 성공·실패와 다시 도전 버튼만 있었다. 축구는 같은 판단도
운에 따라 결과가 갈리므로, 한 판의 점수만 보여주면 좋은 판단을 했는데도
틀렸다고 말하게 된다.

### 세 조건을 같은 150경기로 비교한다

종료 뒤 **무개입 · 사용자가 실제로 내린 판단 · 권장 전술**을 각각 150판
돌린다. 세 조건에 똑같은 시드 묶음을 주었다. 서로 다른 운을 주면 전술
차이와 운 차이가 섞이기 때문이다.

사용자의 판단은 최종 레버 값만 복사하지 않는다. 포메이션·레버·교체·개별
지시를 **실제로 결정한 틱 그대로** 다시 적용한다. 늦은 교체는 다시 돌려도
늦게 듣고, 중간에 바꾼 지시는 그 시점부터만 반영된다.

### 권장 전술은 국면 데이터다

권장 포메이션·레버·설명은 `problems.json`에 넣었다. 새 국면을 추가할 때
같은 데이터 덩어리에 적으면 분석 화면을 고칠 필요가 없다. 추천값은 새로
추측하지 않고 기존 1200시드 전수 검증의 국면별 1위를 썼다.

- 길이 막혔다 — 3-4-3 · 2/1/2
- 잠긴 문 — 4-3-3 · 1/1/2
- 한 명이 없다 — 5-4-1 · 1/2/2

### 화면에서 끝까지 확인했다

잠긴 문을 실제 75초 동안 방치해 1-1로 끝낸 뒤, 종료 화면에서
**무개입 49.3% · 나의 판단 49.3% · 권장 전술 72.0%**가 표시되는 것을
확인했다. 한 판 결과는 실패지만 판단은 방치와 같다고 따로 말한다.

분석 코드는 `src/analysis/`에 두었다. `src/sim/`과 확률 숫자, 매 틱 난수
18개는 건드리지 않았다. 전체 검증 결과도 기존과 한 자리도 다르지 않다.
테스트 194개 → 197개.

## 2026-07-28 (화) 밤 — 경기 화면의 우선순위를 다시 세우다

기존 화면은 포메이션 9개, 선수 명단, 벤치, 기록, 전술 레버, 상황 설명이
같은 무게로 길게 이어졌다. 기능은 많았지만 375×812 폰에서 준비 화면이
1939px였고, 사용자가 가장 먼저 해야 할 전술 조작은 한참 아래 있었다.
데스크톱도 세 열 사이에 피치가 끼어 작아져 관전 화면의 중심이 흐렸다.

`ZOXEXIVO/open-football`에서는 **피치를 크게 두고 탭으로 한 영역씩 여는
정보 구조**만 참고했다. 이 원칙을 우리 문제에 맞춰 점수·상황·목표를 붙인
고정 맥락, 큰 피치, 전술/포메이션/선수/기록 탭으로 재설계했다. 외부 코드,
컴포넌트, CSS, 색, 문구, 이미지, 선수 데이터는 가져오지 않았다.

포메이션은 3×3 이름표로 압축하고 선택한 설명만 남겼다. 전술 프리셋은
마우스를 올려야 보이던 설명을 버튼 안에 항상 보여줘 폰에서도 선택 전
효과와 대가를 알 수 있게 했다. 세부 레버는 필요할 때만 여는 고급 조정으로
내렸다. 분석 화면은 세 확률의 차이를 숫자로 보이고, 권장 설정을 포메이션·
라인·압박·폭 네 칸으로 나눴다.

무개입·나의 판단·권장 전술을 비교하던 기존 150판을 늘리지 않았다. 이미

종료 화면은 감독 총평 다섯 줄, 경기의 전환점, 득점·실점 장면, 결정 평가,

각 근거가 어느 쪽인지 문장에 드러낸다.

시뮬 로그에 없다. 따라서 특정 선수의 실수나 압박 실패, 크로스 위치 같은
세부 원인은 단정하지 않는다. 이 수준이 필요해지면 먼저 읽기 전용 관찰
데이터를 설계하고 `game-agent` 검토를 받아야 한다.

## 2026-07-29 (수) — 주장 보고가 실제 팀 상태를 바꾼다

확인했다. 브라우저에서는 「잠긴 문」의 팀 전체 회복과 「길이 막혔다」의

## 2026-07-29 (수) — 상하 지시 드래그를 실제 자유 좌표로 바꿨다

사용자가 같은 문제를 다시 제보한 이유는 버그 하나가 남아서가 아니라,
우리가 요구를 잘못 정의했기 때문이다. “포지션을 드래그해서 바꾼다”를
기존 `PUSH_UP`·`DROP_BACK` 지시의 빠른 입력으로 좁혔다. 가로 이동과
빈 공간은 원위치, 같은 줄의 다른 선수는 화면에서만 자리 교환이었다.
전용검사 28개와 QA도 그 제한을 정상으로 확인했으므로 모두 통과해도
사용자가 원한 자유 배치는 존재하지 않았다.

새 계약은 `PlayerPosition { x, y }`와 `POSITION` 결정이다. 카드를 놓은
실제 피치 미터를 저장하고, 실시간 상태·결정 재현·종료 분석·중앙 경기장이
같은 값을 읽는다. 위·아래뿐 아니라 가로·세로·대각선을 모두 하나의
`PLACE`로 읽는다. 같은 카드 위에 놓아도 자리를 맞바꾸지 않고, 누르기
표적이 겹칠 때만 가장 가까운 빈곳으로 최소 보정한다.

위치가 화면 장식이면 “영향 없는 조작은 넣지 않는다”는 규칙과 충돌한다.
전진과 측면 폭은 우리 공격 전개를 늘리지만 상대 오픈플레이와 배후 위험도
함께 늘린다. 후퇴와 중앙 밀집은 반대다. 한쪽만 좋아지게 만들면 전원을
상대 골문이나 터치라인에 붙이는 만능 배치가 생기므로 이득과 대가를 같은
방향으로 묶었다. 한 선수의 최대 변화는 약 4%, 합계는 24% 상한이다.

직접 배치한 선수가 없을 때는 새 계수 경로가 `null`을 반환하고 기존
계수 객체를 그대로 돌려준다. 이 덕분에 기존 다섯 국면과 매 틱 난수 18개
순서는 바뀌지 않는다. 골키퍼·피치 밖·수비 셋 미만은 `checkPosition()`이
한 곳에서 막는다.

앞뒤 줄 지시와 직접 좌표가 동시에 남아 어느 것이 진짜인지 갈리지 않게
마지막 위치 지시가 이긴다. 직접 좌표는 `PUSH_UP`·`DROP_BACK`을 풀고,
그 둘을 새로 걸면 자유 좌표가 지워진다. 행동 지시 세 종류는 같이 남는다.
포메이션을 고르는 행위는 전체 재배치라 모든 자유 좌표를 지운다. 사용자가
처음 제보한 “드래그 뒤 포메이션을 바꾸면 카드가 겹침”도 이 규칙으로
막는다.

마우스가 없는 환경에는 수비·중원·공격 × 왼쪽·중앙·오른쪽 아홉 버튼과
기본 자리 버튼을 제공했다. 브라우저에서 가로·대각선·세로 드래그 세 명이
서로 다른 좌표에 남고 `배치 3`이 되는 것, 5-4-1 선택 뒤 `배치 0`과
새 대형으로 돌아오는 것을 확인했다. 자동검사 330개와 생산용 빌드가
통과했고, 새 탭 오류·경고와 1280px 가로 넘침은 0건이었다. 1,200시드
균형 검사도 다섯 국면 모두 합격했고 무개입 기준선
11.0 / 48.0 / 48.1 / 37.2 / 18.5%가 그대로였다.
