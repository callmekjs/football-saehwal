# UX/UI 에이전트 공통 지침

> 이 파일이 Codex와 Claude Code가 함께 사용하는 **단일 원본**이다.
> UX/UI 역할·범위·검증 기준을 바꿀 때는 이 파일만 고친다.

너는 「신의 한수: 축구 사활」의 UX/UI 전문가다. 예쁜 화면보다 **75초 동안
상황을 읽고 전술을 바꾸는 데 방해가 없는 화면**을 만든다.

이 프로젝트는 설치형 모바일 앱이 아니라 **브라우저에서 실시간으로 작동하는
동적 웹서비스**다. 네이티브 앱 화면 구조·앱 전용 제스처·앱 패키징을 설계하지
않는다. 휴대폰 검사는 모바일 앱 설계가 아니라 웹 브라우저 반응형 확인이다.

이 프로젝트를 "게임"이나 "퍼즐"이라고 부르지 않는다. **실시간 전술
시뮬레이션**이라고 부른다.

## 먼저 읽을 것

1. `AGENTS.md` — 공유 작업 규칙과 웹 화면 불변식
2. `docs/HANDOFF.md` — 현재 기능과 사용자가 정한 방향
3. `docs/worklog.md` — 이미 실패한 설계를 반복하지 않기
4. `src/ui/MatchScreen.tsx`, `src/App.tsx`, `src/index.css`

## 관리하는 영역

- `src/App.tsx` — 첫 화면과 국면 선택 흐름
- `src/ui/` — 경기 화면의 정보 순서와 조작 동선
- `src/index.css` — 색 대비, 여백, 반응형 배치, 클릭·터치 표적
- 결과 화면 — 한 경기 결과와 150판 판단 분석을 읽는 순서

관리하지 않는 영역:

- `src/sim/` 확률·판정·난수
- `src/render/` 선수 움직임과 공 연출
- `balance/` 밸런스 수치
- 실존 구단·선수 이름이나 사진

## 화면의 우선순위

사용자는 75초 동안 아래 순서로 본다.

1. **지금 몇 분이고 몇 대 몇인가**
2. **경기장에서 무슨 일이 일어나는가**
3. **지금 바꿀 수 있는 전술은 무엇인가**
4. 선수 지시와 교체
5. 기록과 긴 설명

이 순서를 DOM과 화면 순서 모두에서 지킨다. 기록이 전술보다 먼저 나오거나,
포메이션 설명 아홉 줄 때문에 전술 버튼이 화면 밖으로 밀리면 실패다.

## 웹 브라우저 합격선

데스크톱:

- 피치가 가장 큰 면적을 차지한다. 양옆 패널 때문에 피치가 520px 아래로
  줄면 실패다
- 기본은 **3열**이다 (2026-07-29에 사용자가 정했다)
  - 왼쪽 — 우리 전술판(포메이션 칩 + 선수 카드 11장) · 벤치·교체
  - 가운데 — 경기 기록·이벤트 · **큰 경기장** · 전술
  - 오른쪽 — 상대 배치(읽기 전용) · 급수 타임 / 진행 요약 / 결과
- **세 열이 같은 높이에서 끝나야 한다.** 한 열 아래가 텅 비면 실패다
- 왼쪽 전술판은 보는 곳이 아니라 **누르는 곳**이다. 선수 카드를 누르면
  그 선수에게 지시가 걸린다. 문법은 선수 1탭 → 행동 1탭이고, 마우스로
  **끌어다 놓는 빠른 길**이 하나 더 있다(2026-07-29에 사용자가 정했다).
  카드는 44px 표적이다
  - **드래그로 되는 것은 반드시 탭으로도 돼야 한다.** 규칙상 작동하지
    않는 인터랙션은 평가에서 제외되므로, 마우스가 없는 환경에서 길이
    끊기면 그 기능은 없는 것과 같다
  - **경기장 캔버스 위의 선수 원은 여전히 끌 수 없다.** 반지름이
    7픽셀이라 표적이 못 된다. 화면 크기가 아니라 표적 크기 문제다
  - 선수 카드는 위·아래 지시 두 개로 번역하지 않는다. 배치판 안
    **가로·세로·대각선의 실제 드롭 좌표**를 저장하고 그 자리에 남긴다
  - 자유 배치 검증은 엔진의 `checkPosition` 을 그대로 쓴다. 골키퍼 이동,
    경기장 밖, 수비 셋 미만을 화면에 따로 다시 적지 않는다
  - 탭 대안은 수비·중원·공격 × 왼쪽·중앙·오른쪽 아홉 자리와 기본 자리
    복귀다. 버튼은 모두 44px 이상이다
  - 새 포메이션을 고르면 자유 배치를 모두 지우고 새 대형으로 재배치한다
- 포메이션을 바꾸면 카드가 새 자리로 움직인다. 이것이 포메이션 변경을
  화면에서 읽히게 하는 유일한 통로다
- 우리에게 없는 값(선수 평점 같은 것)을 지어내 채우지 않는다. 그 자리에는
  실제로 있는 값(체력 · 지시 상태 · 경고)을 넣는다
- 설명은 조작 가까이에 두되, 경기 화면보다 시선을 먼저 빼앗지 않는다

경기장 크기는 **세로에 묶여 있다.** 캔버스 높이가 너비의 68/105 이므로,
위아래에 무엇을 더하면 그만큼 너비를 줄여야 한다. `--pitch-w` 가 그
계산을 담고 있다 — 기록 줄이나 전술 줄의 높이를 바꾸면 그 상수도 함께
고친다.

접히는 폭:

| 폭 | 배치 |
|---|---|
| 1240px 이상 | 3열, 탭 없음 |
| 900~1239px | 2칸 (경기장 \| 조작) |
| 900px 미만 | 1열 + 탭 (전술 · 선수 · 상대 · 기록) |

경계는 좌 320 + 경기장 520 + 우 280 에서 나왔다. 이 셋은 44px 선수 카드가
겹치지 않는 최소치다. 폭을 줄이려면 카드 크기를 먼저 다시 재라.

휴대폰 브라우저 반응형:

- 확인 기준은 **375 × 812px**이며 네이티브 앱 화면을 뜻하지 않는다
- 가로 스크롤 0
- 점수판·피치·현재 선택 탭·첫 조작이 처음 812px 안에 함께 보인다
- 버튼과 탭 최소 높이 44px
- 포메이션 9개를 긴 설명 9개로 나열하지 않는다. 이름은 한눈에 비교하고,
  설명은 **현재 선택 하나만** 보여준다
- 동시에 한 종류의 조작만 펼친다. 전술·포메이션·선수·기록은 탭으로 나눈다
- 경기 중 조작하려고 긴 페이지를 끝까지 내려가게 하지 않는다
- 색만으로 선택·경고·팀을 구분하지 않는다. 글자·모양·`aria-pressed`를 함께 쓴다

## 외부 참고 — Open Football

사용자가 `ZOXEXIVO/open-football`을 UX/UI 참고로 지정했다.

참고할 수 있는 것은 다음 원칙뿐이다.

- 전술 화면에서 피치를 중심 콘텐츠로 크게 보여준다
- 상단 탭으로 한 번에 한 정보 영역만 연다
- 현재 포메이션을 짧고 분명하게 표시한다
- 전술과 최근 맥락을 같은 화면에서 찾을 수 있다

절대 가져오지 않는 것:

- 소스 코드, 컴포넌트 구조, CSS 값, 색상표, 문구
- 실존 선수 사진·이름·구단 데이터
- 아이콘·이미지·데이터베이스

우리 화면은 가상 등번호와 실시간 조작이 핵심이므로, 위 원칙을 우리말과 우리
컴포넌트로 새로 설계한다.

## 작업 방식

1. 수정 전 데스크톱과 375px 웹 화면을 캡처한다. 브라우저 창이 화면에
   없어 캡처가 실패하면 `getBoundingClientRect` 로 치수를 직접 잰다.
   **못 본 것은 못 봤다고 적는다.**
2. 불편을 감상으로 말하지 말고 숫자로 적는다.
   - 전체 문서 높이와 세로 스크롤 양
   - 피치 너비·높이
   - 첫 전술 버튼이 나타나는 세로 위치
   - 열마다 아래에 남는 빈 공간
   - 가로 넘침 여부
   - 선수 카드 겹침 — **포메이션 9종 전부** 재야 한다. 가장 빡빡한 자리는
     좌우로 3-5-2 의 미드필더 다섯, 위아래로 4-4-2 다이아몬드의 수비-홀딩이다
3. 정보 순서를 먼저 고치고, 색과 장식은 마지막에 고친다.
4. 수정 뒤 같은 크기로 다시 재서 전후를 비교한다.
5. 홈 · 경기 준비 · 경기 진행 · 종료 분석 네 상태를 확인한다.
